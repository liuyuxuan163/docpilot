# 代码评审规范

## 目的

代码评审（Code Review）的目标是**提高代码质量与知识共享**，而不是挑错或显示水平。
评审意见应当对事不对人。

## 提交前自检（作者责任）

提交 PR 之前，作者必须完成：

1. 本地测试全部通过
2. 新增/修改的逻辑有对应单元测试（覆盖率不得低于改动前的水平）
3. 自查 diff，删除调试代码与临时打印
4. PR 描述写清楚：**改了什么、为什么改、怎么验证**
5. 若涉及接口变更，同步更新文档与调用方

**单个 PR 建议不超过 400 行有效改动**。超过时应拆分为多个 PR ——
评审质量与 PR 大小呈明显负相关。

## PR 描述模板

```markdown
## 改动内容
- 

## 改动原因
- 

## 验证方式
- [ ] 单元测试
- [ ] 本地手工验证（描述步骤）
- [ ] 已在测试环境验证

## 影响范围
- 是否涉及接口变更：
- 是否需要数据迁移：
- 回滚方案：
```

## 评审人的职责

### 必须在 1 个工作日内响应

收到评审请求后，评审人应在 **1 个工作日**内给出首轮意见（可以先给初步意见）。
超过 1 天未响应的，作者可以换人评审或在群里提醒。

### 按优先级标注意见

评审意见需标注严重程度，避免作者无法判断哪些必须改：

| 标记 | 含义 | 是否阻塞合并 |
|---|---|---|
| `[blocker]` | 有正确性/安全性问题 | 是 |
| `[major]` | 设计或可维护性问题，建议修改 | 是（可讨论） |
| `[minor]` | 代码风格、命名建议 | 否 |
| `[nit]` | 吹毛求疵，可忽略 | 否 |
| `[question]` | 没看懂，求解释 | 否 |

### 评审关注点（按优先级）

1. **正确性**：边界条件、空值、并发、异常路径
2. **安全性**：权限校验、注入风险、敏感信息泄露、越权访问
3. **可维护性**：命名、函数长度、职责是否单一、是否有隐式耦合
4. **性能**：是否引入 N+1 查询、是否有不必要的全表扫描、循环内 IO
5. **测试**：是否覆盖了关键分支与失败路径

**风格问题交给工具**（linter、formatter），不要在人评审里争论格式。

## 合并规则

- 至少 **1 位**评审人 Approve 才可合并；核心模块（支付、权限、数据管道）需 **2 位**
- CI 必须全绿：单测、lint、构建
- 作者不得自己 Approve 自己的 PR
- 评审意见全部解决（Resolved）或明确回复"暂不处理 + 原因"后才可合并

## 冲突处理

评审人与作者无法达成一致的：

1. 先线下沟通（15 分钟胜过 20 条评论）
2. 仍不一致时，引入模块负责人做技术裁决
3. 裁决结论需在 PR 里记录，作为后续类似问题的参考

## 常见反模式

| 反模式 | 问题 | 建议 |
|---|---|---|
| "LGTM" 秒过 | 没起到评审作用 | 至少指出 1 个具体点或明确说明已仔细看过关键逻辑 |
| 一次性提 50 条意见 | 作者崩溃、改动引入新问题 | 分优先级，只阻塞 blocker/major |
| 在 PR 里重构无关代码 | diff 变大、难以回滚 | 另开 PR |
| 用"我觉得"下结论 | 无法讨论 | 给出具体理由或反例 |
| 评审拖到 deadline 才看 | 阻塞发布 | 每天固定时段处理评审队列 |
