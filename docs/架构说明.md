# DocPilot 架构说明

本文解释**为什么这么设计**，而不是重复代码在做什么。
建议对照源码阅读：每个小节都标了对应的文件。

---

## 一、整体数据流

一次问答的完整链路（以"年假能结转到明年吗？最多多少天？"为例）：

```
用户提问 + 角色(role)
    │
    ▼
┌─────────────────────────────────────────────────────────────┐
│ agent.Agent.ask()                                           │
│  1. 组装 messages：system 提示词 + 对话历史 + 本轮问题         │
│  2. 进入 ReAct 循环（默认最多 6 步）                          │
└─────────────────────────────────────────────────────────────┘
    │
    │ 每轮：检查预算 → 调 LLM（带工具 schema）
    ▼
┌─────────────────────────────────────────────────────────────┐
│ llm.MockLLM / OpenAICompatLLM                               │
│  返回：content 或 tool_calls[]                               │
└─────────────────────────────────────────────────────────────┘
    │
    ├── 有 tool_calls ──▶ tools.ToolRegistry.execute()
    │                        │
    │                        ├─ ① rewrite_question（指代消解）
    │                        ├─ ② search_docs ──▶ rag 混合检索
    │                        └─ ③ list_documents
    │                        │
    │                     结果回填 messages（role=tool）→ 下一轮
    │
    └── 无 tool_calls ──▶ 视为最终回答
                            │
                            ▼
              ┌──────────────────────────────────┐
              │ 引用映射 + 标号校验 + 拒答识别      │
              │ → core.Answer                     │
              └──────────────────────────────────┘
```

**关键设计**：整条链路上只有一处会"产生文字"（LLM），
其余环节都是**确定性的**。这样出问题时能快速定位到底是检索错了、还是生成错了。

## 二、core.py —— 契约层

### 为什么这层要刻意保持"薄"

只放**跨模块共享的数据结构**与配置读取，不放业务逻辑。
否则它会迅速长成一个什么都往里塞的大杂烩（这是很常见的演化路径）。

### 类型契约

| 类型 | 作用 |
|---|---|
| `Message` | 对话消息，`to_api()` 转成 OpenAI 协议格式 |
| `ToolCall` | 一次工具调用请求 |
| `RetrievedChunk` | 检索结果，`cite()` 产出引用标签 |
| `Citation` | 答案里引用到的来源（带 `[n]` 标号） |
| `Answer` | 一次问答的完整产出，可直接渲染也可直接评测 |

**`Answer` 同时承担两个职责**（展示与评测）是刻意的：
如果为评测另做一套结构，两者必然漂移，最后评测跑的不是线上那条链路。

### `cite()` 为什么只取叶子小节

完整标题路径在嵌套文档里会长成 `员工手册 > 第三章 > 3.2 休假`，
写进答案后完全没法读。所以只取最后一段。

### 错误体系

`DocPilotError` 之下按**是否可重试**分类：

```
DocPilotError          (retryable=False)
├── ConfigError
├── ToolError          (retryable=True)
│   ├── ToolNotFound   (retryable=False)
│   └── ToolDenied     (retryable=False)  ← 未授权/参数越界
├── LLMError           (retryable=True)
│   └── LLMAuthError   (retryable=False)
```

区分"能不能重试"很重要：鉴权失败重试一万次也没用，而网络抖动值得重试一次。

### mini-YAML

约 120 行，覆盖配置文件用到的语法子集：嵌套映射、列表、行内 `[]`/`{}`、
注释、引号、块标量 `|`。

**为什么自己写而不是直接依赖 PyYAML？**
本项目的卖点之一是"零核心依赖，clone 完就能跑"。配置解析只用到很小的语法子集，
用 120 行换掉一个必装依赖是划算的。装了 PyYAML 时会自动优先用它。

内置实现的价值还在**报错可读**：Tab 缩进会说"第 3 行：缩进不允许使用 Tab，请改用空格"。

## 三、matching.py —— 文本匹配（本项目最核心的一块）

这个模块只有 78 行有效代码，但它决定了拒答判定能不能用。

### 为什么不能用中文分词库

分词库（jieba 等）会引入依赖与词典，而且对"制度编号 `HR-2024-07`"这类串不一定友好。
本模块用**不依赖词典**的办法：按标点与虚词切出"实义片段"，再用**字符级最长匹配**测覆盖。

### 虚词必须"断开"，不能"删掉后拼接"

```
❌ 错误做法（去掉虚词后拼接）
   "年假没休完可以结转到明年吗"
   → "年假没休完结转到明年"      ← 现实中不存在的字符串，最长命中变短

✅ 正确做法（虚词作为分隔符）
   → ["年假没休完", "结转到明年"]  ← 真实词组，最长命中更长
```

### 哪些字算虚词：一个需要小心的边界

`的了是在和与或对把被为以及…` 这些显然算。但要注意两类容易误伤的字：

| 字 | 是否虚词 | 原因 |
|---|---|---|
| 办 | ❌ 不是 | "怎么办"里的"办"是实义字，切掉会把"出差住酒店超预算"切碎 |
| 久 | ❌ 不是 | "多久"里的"久"是实义字 |
| 可 / 以 | ✅ 是 | "**可以**结转"不断开会产生"年假没休完可"这种带半截虚词的长片段 |

**这个表是实测调出来的，不是拍脑袋定的。**

### `_best_match`：递归切分

整段问题常被切成一个长片段（`出差住酒店超预算`），它在文档里几乎不可能原样出现。
所以找不到整段时，就**试着把它切开**再匹配，深度限制 2 层避免组合爆炸。

这本质上是一个轻量分词：**在文档里找不到整段时，就切开找子短语**。

### `span_coverage` 返回两个值

| 返回值 | 用途 |
|---|---|
| `coverage` | 问题实义字符中能在文档里找到的比例 → 排序与"有没有依据" |
| `longest_span_ratio` | 最长连续命中 / 问题实义字符总数 → 区分"整句对上"与"零散撞字" |

## 四、rag.py —— 检索层

### 4.1 切块：结构优先 + 长度收敛

```
Markdown
  → 按标题切分（保留章节路径：员工手册 > 第三章 > 年假额度）
  → 段内按句子边界聚合到 chunk_size
  → 去重（blake2b 内容哈希）
  → 生成稳定 chunk_id（source + section + 内容前缀）
```

保留章节路径的两个用处：① 引用能精确到小节；② 过滤时可按章节标签筛。

#### 4.1.1 一个被实验推翻的假设：`chunk_size` 在本语料上近乎失效

这一节记录一次**真实的实验结果**，因为它推翻了我原本写在文档里的预测。

`scripts/experiment_chunk_size.py` 把 `chunk_size` 设为 150 / 360 / 800 各跑一遍：

| chunk_size | 片段数 | composite | retrieval_hit | answer_coverage |
|---|---|---|---|---|
| 150 | **111** | 0.931 | 0.9524 | 0.9048 |
| 360 | 75 | 0.931 | 0.9524 | 0.9048 |
| **800** | **75** | 0.931 | 0.9524 | 0.9048 |

**两个反直觉的观察**：

**观察一：800 与 360 的片段数完全相同 —— `chunk_size` 已经失效。**

根因在贪心拼接的判定上：

```python
candidate = f"{buf}\n{para}".strip() if buf else para
if len(candidate) <= chunk_size:      # ← chunk_size=800 时这里永远为真
    buf = candidate
    continue
```

示例文档是**小节密集型**的，单个自然段最长只有 **247 字符**。
当 `chunk_size > 247` 时，判定恒成立，于是**每个段落各自成块、从不合并** ——
切块粒度实际上由 **Markdown 的小节结构**主导，参数失去了作用。

**这不是 bug，而是"参数有适用区间"。** 用一个 300 句的长段落做对照实验即可验证：

```
chunk_size=150 → 最长块 198 字符
chunk_size=360 → 最长块 408 字符
chunk_size=800 → 最长块 849 字符     ← 参数在长段落上真正生效
```

> **可迁移的结论**：切块粒度由 `chunk_size` **和文档结构**共同决定。
> 在小节密集的语料上调 `chunk_size` 收益有限 —— 想让它生效，得先有长段落。

**观察二：端到端指标完全不变 —— 评测指标的分辨率不够。**

评测集的 `expected_sources` 是**文件级**的（如 `hr/leave-policy.md`），
而切块只改变"文件内部怎么分"，**不改变"命中哪个文件"**。

于是我犯了一个设计层面的错误：**指标的作用层级与参数的作用层级不匹配** ——
却期待它能反映后者的变化。

**要观察到切块的影响，评测集必须精确到片段级**（期望某个具体 chunk_id）。
这是一个**值得记住的通用教训**：

> **设计指标时，先想清楚"这个指标能分辨什么量级的变化"。**
> 一个文件级的指标对片段级的改动天然不敏感，这不是指标错了，
> 而是它被用在了它分辨不了的粒度上。

**顺带一个有价值的副产品**：`chunk_size=150` 让索引规模涨了 48%
（75 → 111 个片段），但 `over_refusal_rate` 仍是 **0.0** ——
说明**拒答阈值对切块粒度是鲁棒的**，它不是一个"对着某种切块方式过拟合"的结果。


### 4.2 分词：bigram + trigram

- **bigram** 保召回
- **trigram** 提区分度
- **同义词双向扩展**：口语（"年假"）↔ 书面语（"带薪年休假"）
- **n-gram 必须过滤纯虚词组合**：`"的了是在"` 会产出 `的了`/`了是`/`了是在`，
  它们不仅无效，还会污染倒排索引与 IDF

### 4.3 BM25

自己实现而不是装 `rank_bm25`，为了零依赖 + 可增量 + 可序列化。

包含 **BM25+ 的下界修正**（`delta` 项）：`idf × [(tf(k1+1))/(tf+norm) + delta]`。
作用是避免长文档因为词频被归一化而系统性低估。
`delta` 的原始论文出发点正是**长文档在长查询下被不公平惩罚**。

### 4.4 稠密检索：LocalEmbedder

```
token → blake2b 哈希 → 64 位整数
      → 取最低位当符号（±1）→ 投影到 dim 维
      → 权重 = (1 + log(tf)) × (trigram 加成)
      → L2 归一化
```

**它没有神经嵌入的语义泛化能力**，但在"领域术语密集的企业文档"上配合 BM25 已经够用，
换来零依赖、零成本、**完全可复现**。

最后一点最关键：检索结果不确定，就没法对检索质量写回归测试。

#### 4.4.1 消融：稠密通道实际贡献了多少？

"要不要换真实 embedding"这个问题，在写代码之前就能先测出一个事实依据。
`scripts/experiment_dense_channel.py` 用 `rag.enable_dense` / `rag.enable_sparse`
做三组对照，并统计"最终 top-4 里有多少条是只有稠密通道能找到的"。

实测（21 条用例）：

| 变体 | 复合分 | 检索命中 | 拒答正确 | 幻觉率 | 误拒率 | p95 |
|---|---|---|---|---|---|---|
| full（双通道） | 0.9310 | 0.9524 | 0.8571 | 0.1429 | 0.0000 | 67.2 ms |
| sparse_only（只 BM25） | **0.9310** | **0.9524** | **0.8571** | **0.1429** | **0.0000** | 54.5 ms |
| dense_only（只本地嵌入） | 0.8905 | 0.9048 | 0.8571 | 0.0952 | 0.0476 | 50.7 ms |

通道贡献（21 条用例 × top-4 = 84 个槽位）：
full 下 `both=34`、`sparse_only=48`、`dense_only=2`，而那 2 个稠密独有槽位**全部出现在
`refuse-03`**（已知幻觉用例）上。

三个结论：

1. **关掉稠密通道，质量指标一模一样**（逐例复合分都相同）。它带来的只有 +12.7 ms 延迟
   和 +23.5 token/次。
2. 原因不是"本地嵌入太差"，而是**语义信号根本没进入判定**：排序主键是 `relevance`
   （词面），`has_evidence` 也是词面 + 最长连续命中。
3. 指标对**候选池的组成**敏感，而不是对"语义能力"敏感 —— 单开稠密时幻觉率反而更低
   （0.0952），代价是检索命中下降、出现 1 条误拒（0.0476）。

> 这个实验的价值在于**它推翻了一个看起来很合理的计划**：
> "本地嵌入没有语义泛化能力 → 换真实 embedding → 幻觉率下降"。
> 前两步成立，第三步不成立 —— 中间缺的是"判定逻辑用上语义信号"。
> 先测再改，比改完发现指标不动更省时间。

要复现：`python scripts/experiment_dense_channel.py`
（原始数据：`evals/reports/dense-channel-experiment.json`）

### 4.5 RRF 融合

```
fused(d) = Σ_r  w_r / (k + rank_r(d))
```

只用排名不用分数，免去量纲对齐。默认 `k=60`（Elasticsearch 等的默认值），
权重 `[1.0, 1.2]` —— 中文短查询里精确词（编号/金额/时限）占比高，稀疏侧略占优。

### 4.6 重排：三个信号

| 信号 | 说明 |
|---|---|
| **IDF 加权覆盖率** | 主力。命中"高区分度片段"比命中"通用短语"更有价值 |
| **字符覆盖率** | 辅助 |
| **最长连续命中** | 辅助，区分"整句对上"与"零散撞字" |

**IDF 加权为什么必要**：`"新员工入职"` 出现在整个 onboarding 文档里几乎每段都沾；
而 `"年假折算"` 只出现在休假办法里。不加权的话，问"新员工年假怎么折算"会被
onboarding 的通用短语抬到第一，而真正写着折算公式的段落掉到第六（实测）。

### 4.7 排序主键的选择 —— 一个真实 bug

最初只用混合 `score` 排序，而 `score` 里含 token 覆盖率与**标题命中**。
结果：问"出差住酒店超预算了怎么办"时，`hr/onboarding.md#常见问题` 排第一
（因为标题里碰巧有"常见问题"），而真正写着"超标部分由个人承担"的
`finance/expense-policy.md#住宿标准` 掉到**第六**。

修复：**relevance 作主序**，融合分只在 relevance 相同时打破平局。
理由是 relevance 语义明确（问题与段落的实义覆盖度），而混合分不可解释。

### 4.8 拒答判定的演进（三个坑）

这是本项目最有教学价值的一段。

#### 坑一：用混合分数做绝对阈值

```python
# ❌ 早期实现
if best_score < 0.3:
    return "没有依据"
```

`best_score` 是 RRF 融合分与覆盖率的加权混合值，**量纲不可比、无法跨查询设固定阈值**。

症状：**引用里明明有正确答案，系统却回答"没有依据"**。
（因为 RRF 分本身量级很小 ~0.02~0.1，覆盖率是 0~1，混合后落在 0.3 附近，恰好卡在阈值上。）

**教训：阈值只能建立在语义明确的指标上。**

#### 坑二：覆盖率会被用户多说的词稀释

```python
coverage = 命中的实义字符数 / 问题实义字符总数
```

实测数据：

| 问题 | 覆盖率 | 应该 |
|---|---|---|
| 公司密码要求多少位？多久必须更换一次？ | 0.29 | 回答 |
| 公司股票代码是多少？ | 0.33 | 拒答 |
| 出差住酒店超预算了怎么办？ | 0.22 | 回答 |
| 公司明年会不会裁员？ | 0.29 | 拒答 |

**区间完全重叠**，无论阈值定在哪都会错一批。
根因：用户问得越啰嗦（"要求""更换一次"），分母越大，分数越低。

#### 坑三：覆盖率的分母本身是错的

用 n-gram 当"主题词"算覆盖率时，分母里塞满了 `占比是`/`工资占`/`效工资`
这类跨词边界的组合，等于**用噪声当分母**。

#### 最终方案：两条语义明确的信号做 AND

| 信号 | 阈值 | 挡掉什么 |
|---|---|---|
| `best_relevance`（IDF 加权覆盖率） | ≥ 0.28 | "今天天气怎么样"这类完全无重合的 |
| `longest_span_chars`（最长连续命中） | ≥ 2 | "公司股票代码"这类只共用"公司/代码"两个字的 |

**为什么要两条**：

- 只看覆盖率 → "公司股票代码"能蹭到 0.58，会被放过；
- 只看连续命中 → 用户多说的词会拉低它，可能误杀正确答案。

阈值由 `scripts/calibrate_thresholds.py` 在 16 条应回答 + 9 条应拒答的标注集上
网格搜索得到，**零误拒**。

**标定结果如实记录**：

```
误拒 0 条，幻觉 3 条（残余）：
  · 公司的股票代码是多少？
  · 公司明年会不会裁员？
  · 竞争对手的核心算法怎么实现的？
```

这三条全部属于"**用词与某段文档高度重合、但实际不构成答案**"。
词面启发式无法分辨"文档提到了这个话题"与"文档回答了这个问题"。
**修它需要真实 embedding 或一次模型判定，而不是继续调阈值** ——
继续调就是对这 21 条评测集过拟合。

### 4.9 权限模型

```yaml
# 文档 front matter
visibility: [public]        # 全员可见
visibility: [hr, finance]   # 仅 HR 与财务可见
```

`allowed_ids(role)` 算出可访问的 chunk 集合，在**检索阶段**就过滤掉无权片段。

**为什么必须在检索阶段而不是生成阶段**：没权限的片段根本不进入上下文，
比"生成后再打码"安全得多 —— 后者只要有一处遗漏就泄漏了。

### 4.10 权限提示：一个容易忽略的漏洞

只做过滤有个漏洞：无权限用户提问"P4 绩效工资占比"时，
系统会**用一份别的文档（差旅住宿标准）来回答** ——
既答错了问题，又暴露了"公司里确实有这份薪酬文档"。

所以 `restricted_matches()` 显式识别"问题指向了受限文档"。
判定**从严**（覆盖率 ≥ 0.55 且比可见文档最好水平高出 0.15），理由很实际：
**权限提示是一句"你不能看"，误报会直接让用户以为系统坏了。**
宁可漏报（退化为普通的"没有依据"）。

## 五、tools.py —— 工具层

### 5.1 为什么只有三个工具

RAG 问答的最小闭环就是「消解指代 → 检索 → 作答」：

| 工具 | 职责 |
|---|---|
| `rewrite_question` | 多轮追问的指代消解 |
| `search_docs` | 混合检索（带权限与证据判定） |
| `list_documents` | 元信息问答（"知识库里有什么"） |

工具多了不涨能力、只涨不确定性。

### 5.2 入参校验：最省钱的拦截点

模型给出越界参数时**在本地拒绝**，比让错误请求打到检索层或模型层再失败便宜得多。

几个容易写错的地方：

- **`bool` 是 `int` 的子类**，必须显式排除，否则 `True` 会被当成合法的 integer 1；
- 未声明的参数**放行**（向前兼容），不报错；
- 校验通过后**补全默认值**。

### 5.3 角色由框架注入，模型无法伪造

```python
if tool.needs_role:
    normalized["role"] = role     # ← 覆盖模型传入的任何 role
```

这是安全上的硬要求：**权限参数绝不能交给模型决定**。
即使模型在参数里传 `role: "hr"`，也会被框架注入的真实角色覆盖
（`test_role_is_injected_and_cannot_be_forged` 锁定了这个行为）。

### 5.4 证据判定放在工具层

`has_evidence` 由 `search_docs` 算好放进 payload，模型与 Mock 拿到的是**结论**，
而不是让每个调用方自己猜阈值。

**阈值只应有一处定义。**

### 5.5 截断：缩字段，不要切字符串

工具结果会按字符数截断后才喂给模型。直接切序列化后的 JSON 会把结构切坏（少括号、字符串没闭合），
下游解析失败后会误判成"检索没有结果"。

```
❌ 切字符串
   '{"tool":"search_docs","results":[{"text":"很长很长…'   ← 括号没闭合，解析失败

✅ 缩字段
   _shrink_payload() 把每个长文本字段压到 limit，结构保持合法
```

这一条踩过坑：**引用里明明有正确片段，回答却说"没有检索到"**。

## 六、llm.py —— 双模式

### 6.1 Mock 的定位

**它不是"假装回答"，而是"确定性参考策略"**：

- 按固定剧本调用**真实工具**（真检索、真权限过滤）；
- 最后用工具**真实返回的片段**组织答案，不编造内容。

所以换真实模型后，链路、工具、评测口径完全不变。

### 6.2 决策逻辑

```
① 问题含指代词 且 还没改写 → 调 rewrite_question
② 还没检索过               → 调 search_docs
③ 其余                     → 用检索结果组织答案
```

### 6.3 `_first_user_question` 为什么优先找 `问题：` 标记

ReAct 会把对话历史作为一条 user 消息先塞进去，历史里那句"年假可以结转到明年吗？"
就成了**第一条** user 消息。若直接取第一条，本轮真正的问题
"那最多能结转多少天？"会被彻底忽略 ——
表现是：多轮追问不触发改写、检索用错问句。

框架自己写的 `问题：` 标记是最可信的信号，优先认它。

### 6.4 JSON 修复器

工具结果被截断后，截断点很可能落在 JSON 中间。`_extract_json` 做三步：

1. 直接解析（含 markdown 围栏）；
2. 括号配平补全（补 `]`/`}`、闭合未结束的字符串）；
3. **去掉结尾不完整的成员** —— 截断点常落在 `"text": "内容` 这种键值对中间，
   光补括号会得到 `{"text": "内容": null}` 这种非法结构。
   做法是回退到最后一个完整的 `,` 或 `{`/`[` 之后重新配平。

### 6.5 自动降级

```python
def build_llm(config):
    if provider == "mock":     return MockLLM(...)
    if not api_key:            return MockLLM(...)   # ← 降级而不是抛错
    return OpenAICompatLLM(...)
```

**没配 Key 时降级而不是报错**，是"新同学 clone 完三分钟能跑起来"的关键。

## 七、agent.py —— 主循环

### 7.1 循环体

```
for step in range(1, max_steps + 1):
    if 工具调用数 >= max_tool_calls: 标记预算耗尽并退出
    response = llm.complete(messages, tools=registry.schemas())
    记录 token 与 trace
    if not response.tool_calls:
        视为最终回答，跳出
    for call in response.tool_calls:
        arguments = dict(call.arguments)
        if call.name == "rewrite_question":
            arguments.setdefault("history", recent)   # ← 框架注入历史
        result = registry.execute(call.name, arguments, role=role)
        结果回填 messages
```

### 7.2 预算耗尽要给"部分结论"

步数用尽时不能空手而归 —— `_partial_answer()` 用已检索到的片段给一个降级结论，
并标记 `degraded=True`。

### 7.3 引用的映射由框架生成

关键点：**`[n] → 文档` 的映射不依赖模型产出结构化引用**。

- 模型只负责在正文写 `[1]`、`[2]`；
- 框架按检索结果顺序生成映射，并**校验标号范围**；
- 模型若写了 `[9]` 而只检索到 3 条 → 记录到 trace，**不臆造来源**；
- 模型完全没标引用 → 附加前 3 条检索来源作为补充，而不是留空。

### 7.4 拒答时不要附引用

答案里没有 `[n]` 标号，却把 4 个检索片段列成"引用来源"，
会让用户以为系统在拿这些片段当依据（何况它们本来就不相关）。

### 7.5 拒答识别的覆盖面

`_looks_like_refusal` 必须覆盖**权限拒答**：它同样是"没回答问题"。
如果识别不出来，评测会把它当成"答了但答错"，指标就失真了。

## 八、eval.py —— 评测层

### 8.1 四类互相制衡的指标

| 指标 | 权重 | 衡量什么 / 为什么不可替代 |
|---|---|---|
| `retrieval_hit` | 0.30 | 期望文档是否被检索到 —— 检索层出问题，生成层再强也没用 |
| `citation_valid` | 0.25 | 引用是否真实存在（**防伪造来源，企业场景最危险的失败**） |
| `refusal_correct` | 0.25 | **该拒答时是否拒答**（防幻觉） |
| `answer_coverage` | 0.20 | 参考答案要点是否覆盖到（最终业务效果） |

### 8.2 拒答必须双向考核

```python
if case.expect_answer:
    score.refusal_correct = 0.0 if answer.refused else 1.0   # 该答却拒 = 过度拒答
else:
    score.refusal_correct = 1.0 if answer.refused else 0.0   # 该拒却答 = 幻觉
```

**过度拒答与幻觉一样是失败。** 一个什么都不肯回答的助手，用户会直接弃用。
所以 `over_refusal_rate` 单独统计，门禁还定得比较紧（≤ 0.15）。

### 8.3 门禁值按实测能力标定

`refusal_correct` 定在 0.70 而不是 0.85，因为词面启发式拒答存在已知天花板。

> **把门槛定在能力之上，等于没有门槛** —— 它只会训练出"忽略红灯"的坏习惯。

### 8.4 单例失败不影响整体

一条用例抛异常 → 记 0 分并附 `error`，继续跑下一条。
评测跑一半崩掉是最浪费时间的情况。

### 10.1 现有测试覆盖不到的一个盲区

第 4.1.1 节的实验暴露了**测试与评测的设计盲区**：

| 层 | 现在测什么 | 测不到什么 |
|---|---|---|
| `test_rag.py::TestChunking` | 单篇文档切出的块数、块长、章节路径 | **片段数随 `chunk_size` 变化的趋势** |
| `test_eval.py` | 文件级 `retrieval_hit` | **片段级的相关性**（该命中哪个具体 chunk） |

`test_rag.py` 里有这样的断言：

```python
def test_respects_chunk_size(self):
    chunks = chunk_markdown(f"# 标题\n\n{body}\n", source="a.md", chunk_size=120)
    assert all(len(chunk.text) <= 200 for chunk in chunks)   # ← 只测了上界
```

**它只验证"不超过上限"，没有验证"参数确实在起作用"。**
所以"`chunk_size=800` 时参数失效"这个问题，测试是发现不了的。

**要补的测试**（如果继续演进这个项目）：

```python
def test_chunk_size_actually_changes_granularity(self):
    """参数必须真的影响切块粒度，而不是被文档结构完全掩盖。"""
    long_para = "员工享有年假。" * 300            # 长段落，迫使切块逻辑介入
    text = f"# 测试\n\n{long_para}\n"
    small = chunk_markdown(text, "t.md", chunk_size=150)
    large = chunk_markdown(text, "t.md", chunk_size=800)
    assert len(small) > len(large)                # ← 断言"趋势"，而不只是"上界"
```

**这才是能抓住"参数失效"的测试形式** —— 断言**相对趋势**，而不是绝对边界。

## 十一、如果要做成生产系统，下一步该改什么

按优先级：

1. **接真实 embedding —— 但它改的是"召回"，不是"幻觉"。**
   接口目前是**硬构造**在 `KnowledgeBase.__init__` 里，第一步应抽 `Embedder` 协议 + 工厂
   （并加向量落盘缓存，否则评测无法离线复现，每次重建都要联网付费）。
   然后必须接受 4.4.1 的结论：**只换 embedding 不会改变端到端指标** ——
   因为排序主键与拒答判定都只读词面信号。真实 embedding 的位置是口语化提问与同义改写；
   要动 `hallucination_rate`，必须**同时**加一个"这段文字到底回不回答这个问题"的判定
   （cross-encoder reranker，或一次小模型判定）。
   把两件事当成一件做，最可能的结局是"改了很多、指标没动"。
2. **评测集精确到片段级**。现在 `expected_sources` 是文件级，
   分辨不出切块、权重这类"文件内部"的改动（见 4.1.1）。
   生产系统应按 chunk_id 或"关键句是否命中"来标注。
3. **指代消解换成一次小模型调用**。规则式处理不了"它的第二条呢"这类复杂指代。
4. **接真实权限中心**。把 `allowed_ids()` 换成查询企业权限服务，接口不变。
5. **加流式输出**。现在要等全部生成完才显示。
6. **索引换成向量库 + 倒排索引**。纯 Python 内存索引在 75 个片段下很快，
   到十万级 chunk 必须换。
7. **加可观测性**。现在只有内存 trace，生产需要落地到日志/追踪系统。

## 十二、MCP 服务端：把协议边界当成设计问题

`docpilot/mcp.py` 把检索能力以 **MCP（Model Context Protocol）** 对外暴露，
传输是 stdio，规范版本 2025-06-18。它没有新增任何检索或判定逻辑 ——
整层只做三件事：**协议编解码、工具白名单、角色绑定**。

### 12.1 为什么不引官方 SDK

MCP 的 stdio 传输就是"一行一条 JSON-RPC 2.0 消息"。本项目需要的只有五个方法：

| 方法 | 作用 |
|---|---|
| `initialize` | 协商版本、声明 `capabilities.tools`、返回 `serverInfo` 与 `instructions` |
| `notifications/initialized` | 握手完成（**通知，不得回复**） |
| `ping` | 保活 |
| `tools/list` | 返回工具名、描述、`inputSchema`、`annotations` |
| `tools/call` | 执行工具，返回 `content` + `structuredContent` + `isError` |

约 200 行就能覆盖，换来的是**零新增依赖**（与项目"clone 完就能跑"一致）。
代价是规范演进要自己跟 —— 所以代码里每个字段旁边都标了它属于哪一步，
升级时逐条核对，而不是凭印象。

### 12.2 三个容易踩的协议细节

1. **通知不能回复。** 回了响应，宿主会把这条响应当成下一条请求的结果，
   整条流水错位。`handle()` 对没有 `id` 的消息一律返回 `None`。
2. **消息里不能有裸换行。** stdio 用换行分帧。`json.dumps` 会把字符串里的
   `\n` 转义成两个字符，所以天然安全；但**任何 `print()` 都会直接破坏协议** ——
   这就是为什么本服务的人类可读输出全部走 stderr。
3. **工具执行失败不是协议错误。** 参数越界、工具内部异常都应该用
   `isError: true` 放在**结果**里，让宿主模型看到原因并自行决定；只有
   "方法不存在 / 参数结构不对"才是 `-32601` / `-32602`。
   把两者混在一起，宿主就只剩"连接失败"一个信息。

### 12.3 角色为什么必须是部署属性

MCP 的调用方是**宿主里的模型**。如果把 `role` 做成工具参数：

* 任何客户端都能传 `role: "hr"`，直接绕过检索阶段的权限过滤；
* 更糟的是，这个参数会被宿主**自动补全**，用户根本看不到发生了提权。

所以角色来自 `--role` / `DOCPILOT_MCP_ROLE` / 配置 `mcp.role`，并且在
`ToolRegistry.execute` 里通过 `needs_role` 在**参数校验之后覆盖**客户端传值
（`tests/test_mcp.py::test_client_cannot_escalate_role` 锁住）。
一个进程一个角色；多角色就多进程 —— 这是刻意的：**权限是部署事实，不是请求参数**。

### 12.4 复用了什么，没复用什么

| 复用了 | 为什么 |
|---|---|
| `ToolRegistry` 与工具 schema | Agent 的 function-calling schema 直接就是 MCP 的 `inputSchema`，两个前端不可能漂移 |
| `needs_role` 注入 | 一条安全路径只实现一次 |
| `ToolResult.summary()` | 文本块沿用"缩字段而不是切字符串"的截断逻辑 |
| `KnowledgeBase` | 同一个索引、同一套 `restricted_matches` 权限提示 |

| 没暴露 | 为什么 |
|---|---|
| `rewrite_question` | 指代消解是宿主侧职责（宿主本来就持有完整对话） |
| `ask`（整条 ReAct） | 宿主自己就在跑 Agent，双 Agent 会互相抢决策 |

### 12.5 新增的攻击面（如实记）

检索结果会原样进入宿主模型的上下文，于是**文档正文里的恶意指令不再受
`SYSTEM_PROMPT` 约束** —— 那三条纪律只对"我们自己的 Agent"有效。
MCP 侧目前只能做两件事：工具全部只读（`readOnlyHint`）、返回值里只有数据没有指令。
要真正缓解，得在索引侧做注入检测，或在宿主侧把检索内容显式标记为 data。
