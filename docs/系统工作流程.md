## 零、两个阶段（理解全局的前提）

RAG 系统分**两个完全独立的阶段**；加入 MCP 之后多出来的**不是第三个阶段，而是第二阶段的另一个出口**：

```
┌─────────────────────────────────────────────────────────────────────┐
│  阶段一：离线建库（Ingestion）                                        │
│                                                                     │
│    文档 → 切块 → 建索引                                              │
│                                                                     │
│    触发时机：进程启动时跑一次（Agent / CLI / Web / MCP 服务端都会先建）  │
│    产物：倒排索引(BM25) + 向量表 + chunk 元数据（含权限）               │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              │  产物被在线阶段读取（只读）
                              ▼
┌─────────────────────────────────────────────────────────────────────┐
│  阶段二：在线问答（Retrieval + Generation）                           │
│                                                                     │
│    提问 → 改写 → 检索 → 融合 → 重排 → 判证据 → 生成 → 映射引用          │
│                                                                     │
│    触发时机：每次提问                                               │
└─────────────────────────────────────────────────────────────────────┘
              │                                    │
              │ 调用方 = 本项目自己的 Agent          │ 调用方 = 外部宿主（Claude Desktop / Cursor…）
              ▼                                    ▼
┌──────────────────────────────┐    ┌──────────────────────────────────┐
│ 路径 A：内部 Agent            │    │ 路径 B：MCP 出口                  │
│                              │    │                                  │
│ 走完整 ReAct + 收尾四步        │    │ JSON-RPC over stdio（换行分帧）    │
│ 模型由本项目提供               │    │ 模型由**宿主**提供                 │
│ 拒答 / 引用由框架**执行**       │    │ 拒答 / 引用只是**建议**，执行在宿主  │
└──────────────────────────────┘    └──────────────────────────────────┘
```

**两条路径的关系（一句话）**：**共用同一个 `ToolRegistry` 和同一份 `KnowledgeBase`，
区别只在"谁来调、以及调完之后谁负责收尾"。** 这也是为什么 MCP 没有带来第二套逻辑。

**为什么必须先分清阶段**：**离线阶段的产物质量决定了在线阶段的上限。**

> 切块切得不好（比如把一句话劈成两半），在线检索再优化也救不回来 —— 垃圾进，垃圾出。
> 这也是为什么"改 `chunk_size` 后必须重建索引"，否则你调的是新参数、量的还是旧索引。

| | 阶段一（离线） | 路径 A（内部 Agent） | 路径 B（MCP 出口） |
|---|---|---|---|
| 频率 | 进程启动一次 | 每次提问 | 每次工具调用 |
| 成本 | 约 10ms（75 个片段） | 约 60ms（含 LLM 调用） | 约 3ms（纯检索，无 LLM） |
| 代码入口 | `KnowledgeBase.build()` | `Agent.ask()` | `mcp.serve()` |
| 错了怎么发现 | 测试（`test_rag.py::TestChunking`） | 评测（`eval`） | 协议测试（`test_mcp.py`） |
| 谁决定"答不答" | — | 框架（环节 F 的 `has_evidence`） | **宿主模型**（我们只给结论） |

> 路径 B（MCP）**没有 ReAct 循环、也没有第 5~8 步** —— 宿主自己跑它的 Agent，
> 我们只把 `search_docs` / `list_documents` 两个工具交出去，连同"检索 + 判证据"的结果。

## 三、第 0 步：准备

**位置**：`agent.py` 的 `Agent.ask()` 开头

```python
messages: List[Message] = [Message(role="system", content=SYSTEM_PROMPT)]
context = self.conversation.transcript()
if context and history is None:
    messages.append(Message(role="user", content=context))          # 对话历史
messages.append(Message(role="user", content=f"问题：{question}"))   # 本轮问题
```

### 关键设计：历史是一条 `user` 消息

注意对话历史**不是**还原成"user / assistant 交替"的形式，而是**打包成一条 user 消息**。

这是简化设计，但它带来了**整个项目最隐蔽的一个坑**。

### 🔴 坑 1：取第一条 user 消息当问题

| | |
|---|---|
| **位置** | `llm.py` 的 `_first_user_question()` |
| **症状** | 多轮追问不触发改写、检索用错问句 |
| **原因** | 历史是第一条 user 消息。若直接取"第一条 user"，拿到的是历史里那句"年假可以结转到明年吗？"，而本轮真正的问题"那最多能结转多少天？"**被完全忽略** |
| **修复** | 优先找框架自己写的 `问题：` 标记 —— 它是代码写死的、位置确定，最可信 |

```python
# 修复后的顺序
标记 = ("问题：", "问题:")
for message in messages:
    for marker in 标记:
        index = message.content.find(marker)
        if index >= 0:
            return ...   # 找到了就用它
# 找不到才退化为"第一条非历史的 user 消息"
```

## 四、ReAct 循环

**位置**：`agent.py` 的 `for step in range(1, self.max_steps + 1)`

### 循环内的四个动作

```python
for step in range(1, self.max_steps + 1):
    # ① 预算检查
    if len(tool_calls_made) >= self.max_tool_calls:
        budget_exhausted = True
        answer.trace.append({"step": step, "event": "budget", ...})
        break

    # ② 调 LLM
    response = self.llm.complete(messages, tools=self.registry.schemas())

    # ③ 判断是否有工具调用
    if not response.tool_calls:
        answer.text = response.content or ""
        break                                    # ← 拿到最终回答

    # ④ 执行工具
    for call in response.tool_calls:
        arguments = dict(call.arguments or {})
        if call.name == "rewrite_question":
            arguments.setdefault("history", recent)      # 框架注入历史
        result = self.registry.execute(call.name, arguments, role=role)
        tool_calls_made.append(call.name)
        if isinstance(result.payload, dict):
            tool_payloads.append(result.payload)         # ★ 完整数据
        messages.append(Message(role="tool", content=result.summary(), ...))  # ★ 摘要
else:
    budget_exhausted = True                      # ← for...else：跑满步数没 break
```

### 关键设计：一份数据，两种形态

第 ④ 步里**工具结果被保存了两份**，用途完全不同：

| | `messages` 里 | `tool_payloads` 里 |
|---|---|---|
| 来源 | `result.summary()` | `result.payload` |
| 形态 | **字符串**（JSON 文本） | **原始 Python 字典** |
| 是否截断 | ✅ 会（长文本压到 600 字符） | ❌ **完整无截断** |
| 消费者 | **LLM** | **框架自己** |
| 用途 | 让模型知道"检索到了什么" | 引用映射 / 降级兜底 |

> **这个分层是必要的**：模型只需要看个大概，而框架需要用精确数据做引用映射。

### 🔴 坑 10：`for...else` 的语义

| | |
|---|---|
| **位置** | `agent.py` 第 198 行的 `else` |
| **易误读** | 以为它是某个 `if` 的 `else`（循环体内 8 空格缩进处没有 `if`） |
| **真实语义** | **`for` 的 `else`** —— 只在循环"没有 `break` 过"（跑满 `max_steps`）时执行 |
| **作用** | 检测"步数预算耗尽"，与循环内的 `max_tool_calls` 检查**配合覆盖两种预算** |

```python
# 缩进是判据：else 在第 8 列，和 for 同级
        for step in range(1, self.max_steps + 1):     # ← 8 空格
            if len(tool_calls_made) >= ...:           # ← 12 空格
                ...
                break
            ...
        else:                                         # ← ★ 8 空格，属于 for
            budget_exhausted = True
```

### 三种结束方式

| 结束方式 | 代码位置 | 后续 |
|---|---|---|
| `break` — 拿到最终回答 | `if not response.tool_calls` | 正常走第 5~8 步 |
| `break` — 工具额度用尽 | 循环开头 | 触发第 5 步降级 |
| `break` — LLM 调用失败 | `except LLMError` | `degraded=True`，直接收尾 |
| **自然跑完** | `else` 分支 | 触发第 5 步降级 |

## 五、工具① `rewrite_question`

**触发条件**：问题含指代词（`它/这个/那个/那/上面/刚才/…`）

> **MCP 不暴露这个工具。** 指代消解是宿主那一侧的事（宿主本来就有完整对话），
> 把它当工具只会让宿主多绕一步；而且它依赖"上一轮问题"，而外部宿主的会话不由我们管理。
> 所以 `EXPOSED_TOOLS` 里只有 `search_docs` 和 `list_documents`。

### 流程图

```
问题："那最多能结转多少天？"  + history=["年假可以结转到明年吗？"]
        │
        ▼
┌─────────────────────────────────────────────────────┐
│ _rewrite(question, history)          tools.py        │
│                                                     │
│  ① 问题里有指代词吗？                                  │
│     检查 COREFERENCE_HINTS                           │
│     = (它, 这个, 那个, 那, 上面, 刚才, 前面, ...)      │
│     无 → 原样返回（不改写）                            │
│                                                     │
│  ② 从上一轮问题提取主题词                              │
│     _extract_topic(history[-1])                     │
│     → 取最长的中文片段或英文词                          │
│     "年假可以结转到明年吗" → "年假可以结转到明年"?       │
│                                                     │
│  ③ 把指代词替换成主题词                                │
│     "那" → 主题词                                     │
└─────────────────────────────────────────────────────┘
        │
        ▼
输出："结转到下一年最多能 多少天？年假"
        │
        └──► 成为 search_docs 的 query
```

### 🔴 坑 2：指代词表漏了「那」

| | |
|---|---|
| **位置** | `tools.py` 的 `COREFERENCE_HINTS` |
| **症状** | "那最多能结转多少天"不触发改写 → 检索偏 |
| **原因** | 最初只放了"那个"，漏掉单字"那" —— 而"那…"是最典型的多轮追问开头 |
| **修复** | 补上「那」，**并去掉长度阈值判断** |

**⚠️ 一个必须注意的连带要求**：**两张指代词表必须一致**

```
llm.py  _COREFERENCE_HINTS      → 决定"是否触发改写"
tools.py COREFERENCE_HINTS      → 决定"怎么改写"
```

两处不一致会导致"**触发了改写却没生效**" —— 这类 bug 极难排查。

### 另一个相关的坑：长度阈值误判

早期 `_needs_rewrite` 里有这么一句：

```python
if not question or len(question) > 40:      # ❌
    return False
```

**后果**："那最多能结转多少天？有上限吗？"这种稍长的追问直接被跳过改写。

**修复**：**是否依赖上文只取决于"有没有指代词"，与长度无关。**

## 六、工具② `search_docs`（核心链路）

**这是整个 RAG 最复杂的一段，有 7 个子环节（A~G）。**

> **它也是 MCP 暴露的两个工具之一**（另一个是 `list_documents`）。
> 环节 A~G 全部原样复用 —— MCP 层只做协议翻译（JSON-RPC ↔ `ToolResult`），
> 不重写任何检索或判定逻辑。所以"外部宿主看到的权限、引用、`has_evidence`
> 与内部 Agent 完全一致"是**结构保证**，不是靠两边各写一遍对齐。

### 环节 B 与 C：为什么两路都要

| | BM25（稀疏） | 稠密 |
|---|---|---|
| **依据** | **字面**：词出现了吗、几次、文档多长 | **向量夹角**：语义是否接近 |
| **擅长** | 精确词：`HR-2024-07`、`15 个工作日`、`SSO` | 口语改写："年假能攒到明年吗" |
| **弱项** | 同义改写完全召不回 | **编号/金额这类"字面精确但语义相反"完全分不清** |
| **实现** | `BM25Index`（TF 饱和 + 长度归一化 + IDF） | `LocalEmbedder`（哈希投影 + L2 归一化） |

**两者的弱点正好互补** —— 这就是"必须混合"的根本原因。

**验证方式**：看 `sparse_rank` 与 `dense_rank` 的差别 ——
有些片段只在稀疏侧靠前，有些只在稠密侧靠前。

### 环节 E：重排的两个作用

**作用一：精排（可解释）**

用三个信号替代 RRF 的"纯名次"：

| 信号 | 权重 | 含义 |
|---|---|---|
| IDF 加权覆盖率 | 0.55 | 命中的是"稀有实义词"还是"通用词" |
| 字符覆盖率 | 0.25 | 问题的实义字符有多少在段落里 |
| 最长连续命中 | 0.20 | 是"整句对上"还是"零散撞字" |

**作用二（更关键）：产出拒答判定所需的信号**

| 信号 | 谁消费 |
|---|---|
| `metadata["relevance"]` | 环节 F |
| `metadata["longest_span_chars"]` | 环节 F（**主力**） |
| `metadata["margin"]` | 调试与评测 |

> **所以重排不能省** —— 没有它，整个拒答机制就失去基础。

### 🔴 坑 5：排序主键选错（无关文档排第一）

| | |
|---|---|
| **位置** | 环节 E 的排序（`_rerank` 末尾） |
| **症状** | 问"出差住酒店超预算了怎么办"，`hr/onboarding.md#常见问题` 排**第一**，而真正写着"超标部分由个人承担"的 `finance/expense-policy.md#住宿标准` **掉到第六** |
| **原因** | 早期只按混合 `score` 排序，而 `score` 里含**标题命中** —— 那个无关文档的标题碰巧有"常见问题" |
| **修复** | **`relevance` 作主序**，融合分只在 relevance 相同时打破平局 |

```python
# 修复后
chunks.sort(key=lambda c: (-float(c.metadata.get("relevance", 0.0)), -c.score, c.chunk_id))
#                           ↑ 主序：语义明确的实义覆盖度      ↑ 平局才看融合分
```

**为什么这么改**：relevance 语义明确（问题与段落的实义覆盖度），
而混合分**不可解释** —— 你没法说清"0.42 分"好在哪。

### 环节 F：本项目最核心的设计

**拒答与幻觉的分界点。** 判定规则：

```python
has_evidence = (
    bool(results)
    and not restricted                        # 权限优先
    and best_relevance >= 0.28                # 覆盖率达标
    and best_span >= 2                        # 最长连续命中达标
)
```

**为什么要两条信号做 AND**（实测数据）：

```
                     relevance        longest_span_chars
应回答组            0.444 ~ 0.720          4 ~ 5
应拒答组            0.000 ~ 0.579          0 ~ 2
                    ↑ 重叠！                ↑ 干净分开
```

**复现命令**：`python scripts/check_relevance_signals.py`

### 🔴 坑 3：用不可比的混合分数做绝对阈值

| | |
|---|---|
| **位置** | 环节 F（最早的失败版本） |
| **症状** | **引用里明明有正确答案，系统却回答"没有依据"** |
| **原因** | 最早写 `if best_score < 0.3: 拒答`，而 `score` 是 RRF 融合分（量级 0.02~0.1）与覆盖率（0~1）的加权混合值。混合后落在 0.3 附近，**恰好卡在阈值上** |
| **教训** | **阈值只能建立在语义明确的指标上** |

### 🔴 坑 6：用字符覆盖率当判据（区间重叠）

| | |
|---|---|
| **位置** | 环节 F（中间的失败版本） |
| **症状** | 用户问得越啰嗦分数越低；超纲问题能蹭到不低的分 |
| **实测证据** | 见上表 —— 应回答组 min(0.444) **小于** 应拒答组 max(0.579) |
| **原因** | 分母包含无意义 n-gram 与用户多说的词（"要求"、"更换一次"） |

**具体的失败案例**：

```
公司密码要求多少位？多久必须更换一次？   relevance 0.444  → 应回答
公司的股票代码是多少？                relevance 0.579  → 应拒答（反而更高！）
```

**改成"IDF 加权的实义片段覆盖率"后才缓解**。

### 🔴 坑 7：实义片段"删虚词后拼接"

| | |
|---|---|
| **位置** | `matching.py` 的 `significant_spans()` |
| **症状** | 产出 `"年假没休完结转到明年"` 这种现实中不存在的字符串 → 最长连续命中变短 → 命中率下降 |
| **原因** | 最初是"去掉虚词字符后把两边**粘起来**" |
| **修复** | **把虚词当作分隔符**（断开，而不是删掉） |

```python
# ❌ 删掉后拼接
"年假没休完可以结转到明年" → "年假没休完结转到明年"

# ✅ 虚词当分隔符
"年假没休完可以结转到明年" → ["年假没休完", "结转到明年"]
```

**衍生坑**：把「办」（怎么办）、「久」（多久）也当虚词，
会把 `"出差住酒店超预算"` 切碎。**这两个字是实义字。**

### 🔴 坑 8：n-gram 产出纯虚词组合

| | |
|---|---|
| **位置** | `rag.py` 的 `tokenize()` |
| **症状** | `"的了是在"` 产出 `的了`/`了是`/`了是在`，**污染倒排索引与 IDF**（抬高无关文档的 BM25 分） |
| **原因** | 中文 n-gram 在字符层面生成，跨过了词边界 |
| **修复** | n-gram 至少要含一个实义字（`_has_content_char`） |

### 🔴 坑 4：`bool` 被当成合法 `integer`（工具参数校验）

| | |
|---|---|
| **位置** | 执行工具时的 `validate_args`（`tools.py`） |
| **症状** | 模型传 `top_k=true` 能通过校验，被当成 1 使用 —— **看起来能跑，但语义错了** |
| **原因** | `isinstance(True, int)` 在 Python 里是 `True`（bool 是 int 的子类） |
| **修复** | 显式排除 `expected == "integer" and isinstance(value, bool)` |

### 🔴 坑 9：工具结果被截断导致"检索无结果"

| | |
|---|---|
| **位置** | `tools.py` 的 `ToolResult.summary()` → `messages` |
| **症状** | **引用里明明有正确片段，回答却说"没有检索到"** |
| **原因** | 直接对序列化后的 JSON 做**字符截断**，把结构切坏了（少括号、字符串没闭合）。下游 `_extract_json` 解析失败 → 误判为"检索没有结果" |
| **修复** | **缩字段，不要切字符串** —— 先把长文本字段压缩，保持结构合法；并配 JSON 修复器兜底 |

```python
# ❌ 切字符串
'{"tool":"search_docs","results":[{"text":"很长很长…'     # 括号没闭合

# ✅ 缩字段
_shrink_payload() 把每个长文本字段压到 limit，结构保持合法
```

## 八、循环之后：收尾四步

### 第 5 步：降级兜底

```python
if budget_exhausted and not answer.text:
    answer.degraded = True
    fallback = self._partial_answer(tool_payloads)
    answer.text = fallback or "未能在这个问题预算内得出结论，请把问题拆得更具体一些。"
```

**原则**：预算用尽要**给"部分结论"，不能空手而归**。

```python
@staticmethod
def _partial_answer(payloads):
    """降级路径：用已检索到的片段拼一个"部分结论"。"""
    for payload in reversed(list(payloads)):          # 从最近一次往回找
        if payload.get("tool") == "search_docs" and payload.get("results"):
            top = payload["results"][0]                # 取相关度最高的片段
            text = re.sub(r"\s+", " ", str(top.get("text", "")))[:200]
            return f"（因达到步数上限，给出部分结论）根据 `{top.get('citation')}`：{text}…"
    return ""
```

**注意它读的是 `tool_payloads`（完整数据）而不是 `messages`（截断字符串）** ——
否则引用标签可能已经被截掉了。

**测试锁定**：`test_agent.py::test_stops_at_max_steps`

### 第 6 步：引用映射（`_attach_sources`）

```
answer.text（模型写的，含 [1][2] 标号）
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│ _attach_sources(answer, tool_payloads, recent)               │
│                                                             │
│  ① 从 rewrite_question 的 payload 提取 → rewritten_question  │
│  ② 从 search_docs 的 payload 建 chunks 列表                  │
│  ③ 正则找答案里的 [n] 标号                                    │
│  ④ ★ 校验标号范围：有 [9] 但只检索到 3 条 → 记进 trace         │
│  ⑤ 生成 Citation（marker + chunk_id + source + 摘要）         │
│  ⑥ ★ 拒答时直接 return（不附引用）                            │
└─────────────────────────────────────────────────────────────┘
        │
        ▼

    Citation(marker="[1]", chunk_id="ck_...",
             label="hr/leave-policy.md#年假可以结转到下一年吗")
]
```

**核心设计：`[n] → 文档` 的映射由框架生成，不依赖模型产出结构化引用。**

| 情况 | 处理 |
|---|---|
| 模型标了 `[1][2]` | 按检索结果顺序生成映射 |
| 模型标了 `[9]`（越界） | **记录到 trace，不臆造来源** |
| 模型完全没标引用 | 附加前 3 条检索来源作为补充，而不是留空 |
| **拒答** | **不附引用** —— 否则用户以为系统在拿这些片段当依据 |

### 第 7 步：拒答识别

> **只在路径 A 与评测里发生。** MCP 路径下 DocPilot 不产出答案文本，也就没有"拒答文案"可识别 ——
> 那边执行拒答的是宿主模型（我们只提供 `has_evidence` / `restricted_sources` 两个事实）。

```python
if answer.refusal_reason or _looks_like_refusal(answer.text):
    answer.refused = True
    answer.refusal_reason = answer.refusal_reason or "知识库中没有找到相关依据"
```

**必须覆盖三类拒答**：

| 类型 | 关键词 |
|---|---|
| 无依据 | "没有找到"、"知识库中没有任何" |
| 证据不足 | "不足以支撑"、"不做推测"、"无法回答" |
| **权限类** | "没有访问权限"、"无权访问"、"涉及受限文档" |

### 🔴 坑 11：权限拒答没被识别成拒答

| | |
|---|---|
| **位置** | `agent.py` 的 `_looks_like_refusal()` |
| **症状** | 评测把权限拒答当成"答了但答错"，**指标失真** |
| **原因** | 权限拒答的文案是"这个问题涉及受限文档…没有访问权限"，早期关键词表里没有这些词 |

## 九、权限支线（贯穿全流程）

权限**不是独立步骤**，而是贯穿在四个位置：

```
  环节 A  ──────►  环节 F  ──────►  第 6/7 步  ──────►  MCP 启动时
```

| 位置 | 做什么 | 关键点 |
|---|---|---|
| **环节 A** | `allowed_ids(role)` 过滤掉无权片段 | **检索阶段就看不到** —— 无权片段根本不进入打分 |
| **环节 F** | `restricted_matches()` 识别"问题指向受限文档" | **明确告知**，不用别的文档凑答案 |
| **第 6/7 步** | 权限拒答文案 + **不附引用** | "你当前角色没有访问权限" |
| **MCP 启动时** | 角色绑定在进程上：`--role` > `DOCPILOT_MCP_ROLE` > `mcp.role` > public | **绝不作为工具参数** —— 客户端传了也会被覆盖 |

### 为什么过滤必须在检索阶段

```python
# 环节 B：BM25 里就做交集
if allowed is not None:
    candidates &= allowed          # ★ 无权片段根本不进入打分
```

**对比"生成后再打码"**：后者只要有一处路径遗漏就泄漏了。
**在检索阶段过滤，无权内容根本不进入上下文** —— 这是安全边界，不是体验优化。

### 🔴 坑 12：只做过滤会"拿别的文档凑答案"

| | |
|---|---|
| **位置** | 环节 F 的 `restricted_matches()` |
| **症状** | 无权限用户问"P4 绩效占比"，系统**拿差旅住宿标准来回答** —— ① 答错了问题 ② **暴露了"存在这份薪酬文档"** |
| **修复** | `restricted_matches()` 识别"问题明确指向受限文档"时返回无权限提示 |

**判定刻意从严**：

```python
if coverage >= 0.55 and coverage >= visible_best + 0.15:
    # 覆盖率够高，且明显优于可见文档
```

**为什么要从严**：**误报"你无权访问"会让用户以为系统坏了。**
宁可漏报（退化为普通的"没有依据"），也不要因为沾了一两个词就喊"无权限"。

## 十、十五个坑的环节索引

**按环节排序，便于定位**：

| # | 坑 | 环节 | 症状关键词 | 源码位置 |
|---|---|---|---|---|
| 1 | 取第一条 user 消息当问题 | 第 0 步准备 | 多轮追问不触发改写 | `llm.py::_first_user_question` |
| 2 | 指代词表漏「那」 | 工具① 改写 | "那…"不触发改写 | `tools.py::COREFERENCE_HINTS` |
| 3 | 用混合分数做绝对阈值 | 环节 F 证据判定 | **命中却说"没有依据"** | `tools.py::build_registry` |
| 4 | `bool` 当合法 `integer` | 执行工具时校验 | `top_k=true` 通过校验 | `tools.py::validate_args` |
| 5 | 排序主键选错 | 环节 E 重排 | 无关文档排第一 | `rag.py::_rerank` |
| 6 | 用覆盖率当判据 | 环节 F 证据判定 | 区间重叠，两边都错 | `tools.py` + `matching.py` |
| 7 | 实义片段"删虚词后拼接" | 环节 E 前置 | 最长命中变短 | `matching.py::significant_spans` |
| 8 | n-gram 产出纯虚词组合 | 建库分词 | 污染 IDF | `rag.py::tokenize` |

| 10 | `for...else` 语义 | 第 5 步降级 | 步数耗尽检测 | `agent.py` 第 198 行 |
| 11 | 权限拒答没被识别 | 第 7 步拒答识别 | 评测指标失真 | `agent.py::_looks_like_refusal` |
| 12 | 只过滤不提示权限 | 权限支线 | **拿别的文档凑答案** | `rag.py::restricted_matches` |
| 13 | 日志写进 stdout | MCP 出口 | 宿主解析失败、直接断连 | `mcp.py::main`（只写 stderr） |
| 14 | UTF-8 BOM 让首条消息解析失败 | MCP 出口 | `initialize` 返回 -32700，现象是"连不上" | `mcp.py::serve` 的 `lstrip("\ufeff")` |
| 15 | 通知被回复 / 工具失败当协议错误 / 声明未实现的能力 | MCP 出口 | 客户端异常、模型看不到失败原因、卡在列表请求 | `mcp.py::handle` 与 `_call_tool` |

### 按"失败类型"分类（另一种视角）

| 失败类型 | 涉及的坑 | 共同特征 |
|---|---|---|
| **答案不可信** | 3, 6, 9, 12 | 用户拿到错误结论，且**系统不报错** |
| **该答却拒答** | 3, 6 | 用户以为系统坏了 |
| **排序错了** | 5, 7, 8 | 相关内容排到后面 |
| **多轮失效** | 1, 2 | 追问场景完全失灵 |
| **评测失真** | 11 | 指标算错，**比效果差更危险** |
| **协议层断连** | 13, 14, 15 | 宿主连不上，而服务端日志看起来"一切正常" |
| **参数静默失效** | （建库）切块 | 调了参数但什么都没发生 |

> **共同特征**：**没有一个会报错。** 它们只是"悄悄给出错误结论" ——
> 这也是为什么本项目把"评测 + 单元测试 + 门禁"放在和功能同等重要的位置。

## 十二、三个最容易搞混的点

### ① 两路召回 ≠ 一次检索

初学者容易以为"检索"是一个动作。实际上：

```
        查询
         │
    ┌────┴────┐
    ▼         ▼
  BM25      稠密      ← 两条独立通道，各自取 top-8
    │         │
    └────┬────┘
         ▼
       RRF 融合        ← 才合成一份
```

**验证**：看结果的 `sparse_rank` 与 `dense_rank` ——
两者不同，说明确实走了两条路。

### ② RRF 融合 ≠ 重排

| | RRF 融合（环节 D） | 重排（环节 E） |
|---|---|---|
| **输入** | 两个**排名列表** | 一份**候选列表** |
| **依据** | **只用名次** | **内容相关性**（覆盖率等） |
| **能解释吗** | ❌ 只看"第几名" | ✅ 能说出"覆盖率 0.72、连续命中 4 字" |
| **目的** | 合成一个排名 | 精排 **+ 产出拒答信号** |
| **能省吗** | 能（但会失去一路） | **不能**（拒答机制依赖它） |

### ③ 拒答判定在检索阶段，不在生成阶段

```python
# 环节 F：search_docs 算好后放进 payload
"has_evidence": has_evidence

# MockLLM 只是"读结论"，不自己判断
if not payload.get("has_evidence", False):
    return "知识库中没有..."
```

**这是刻意的**：

| 理由 | 说明 |
|---|---|
| 阈值只应有一处定义 | 若让模型判断，每个调用方都要自己定阈值 |
| 不能依赖模型自觉 | 模型可能"觉得"有依据就答了 |
| 可测试 | 结论是代码算的，能写单元测试断言 |
| **MCP 路径是例外** | 最终执行者是宿主模型。我们只能把结论放进 `has_evidence`、并在 `INSTRUCTIONS` 里要求它遵守（见第十三节） |

## 十三、MCP 出口：把同一套检索暴露给外部宿主

**位置**：`mcp.py`（341 行，零依赖手写）· 入口 `python -m docpilot mcp --role public`

### 为什么单独有这个出口

CLI / Web / Agent 三个前端都只能**在本项目内部**用。MCP 把 `search_docs` 变成
**任何宿主都能挂载的能力**（Claude Desktop / Cursor / Cline 配一行 JSON 就能用同一份知识库），
而且行为与内部 Agent 完全一致 —— 因为它**复用同一个 `ToolRegistry`**，不是另写一套。

### 流程图

```
宿主（Claude Desktop / Cursor …）
   │  ① initialize（protocolVersion + clientInfo）
   ▼
┌────────────────────────────────────────────────────┐
│ mcp.serve()                            mcp.py      │
│  · 一行一条 JSON-RPC 2.0（stdio，换行分帧）           │
│  · 容忍 UTF-8 BOM；坏消息回 -32700 后**继续读**        │
│  · 只实现 5 个方法：initialize / notifications/      │
│    initialized / ping / tools/list / tools/call     │
└────────────────────────────────────────────────────┘
   │  ② 返回 protocolVersion + capabilities{tools} + serverInfo + instructions
   │  ③ notifications/initialized（通知 → **不回复**）
   │  ④ tools/list → 2 个工具 + inputSchema + readOnlyHint
   │  ⑤ tools/call {"name":"search_docs","arguments":{…}}
   ▼
┌────────────────────────────────────────────────────┐
│ registry.execute(name, args, role=服务端角色)        │  ← 与内部 Agent 同一份注册表
│  · role 在这里注入：客户端传了也会被覆盖                 │
│  · 复用 schema 校验 / 权限过滤 / has_evidence 判定     │
└────────────────────────────────────────────────────┘
   │  ⑥ 返回 CallToolResult
   │     content: [{type:"text", text: summary()}]        ← 给模型读（已缩字段）
   │     structuredContent: payload（完整、含 citation）   ← 给宿主程序用
   │     isError: false
   ▼
宿主模型读片段 → 自己组织答案（写 citation / 遵守 has_evidence）
```

### 四个刻意的设计决定

| 决定 | 理由 |
|---|---|
| **只暴露 2 个工具**（`search_docs` / `list_documents`） | 不暴露 `rewrite_question`：指代消解是宿主的事（它本来就有完整对话）；**不暴露整条 `ask`**：宿主自己就在跑 Agent，再塞一个自带循环的 Agent 属于"双 Agent 反模式"，会互相抢决策 |
| **角色在服务端绑定**（`--role` > `DOCPILOT_MCP_ROLE` > `mcp.role` > public） | 权限是**部署属性**，不是请求属性。客户端若能把 `role` 当参数传，等于允许自称 HR；`needs_role` 在参数校验**之后**覆盖同名字段，`test_mcp.py` 有专门的提权测试锁住 |
| **stdout 是协议通道，日志只能进 stderr** | 一句 `print()` 就污染 JSON-RPC 流，宿主直接断连 —— 这类服务端最常见的事故 |
| **工具失败用 `isError`，不是协议错误** | 执行失败属于**结果**：宿主模型能看到原因，自己决定换问法还是放弃；`-32602` 才表示客户端把请求写错了 |

### MCP 改变了什么、没改变什么

| | 没变 | 变了 |
|---|---|---|
| 检索与权限 | 同一份 `KnowledgeBase`、同一套 `allowed_ids` | — |
| 证据判定 | 仍在环节 F 算好、放进 payload | 从**"执行"**变成**"建议"**：真正决定答不答的是宿主里的模型 |
| 拒绝与引用 | 仍然有 `citation` 字段、`restricted_sources` | 不再由 `_attach_sources` / `_looks_like_refusal` 收尾（这两步只服务内部 Agent 与评测） |
| 安全边界 | — | 检索结果**原样进入宿主上下文**，文档里的恶意指令不再受 `SYSTEM_PROMPT` 约束（见已知限制） |

> 所以「拒答判定在检索阶段」这句话在 MCP 路径下要加限定：
> **我们只负责给出判定结论，执行者是宿主。** 这也是 `INSTRUCTIONS` 存在的意义。

### 本节的坑

| 坑 | 位置 | 症状 |
|---|---|---|
| **日志混进 stdout** | `main()` 的 `print(..., file=sys.stderr)` | 宿主解析失败、直接断连，而服务端看起来"启动正常" |
| **UTF-8 BOM** | `serve()` 的 `lstrip("\ufeff")` | 首条 `initialize` 变 `-32700`，现象是"宿主连不上" |
| **回复了通知** | `handle()` 里 `if is_notification: return None` | 规范规定通知不得回复；多一条响应会让客户端状态错乱 |
| **声明了没实现的能力** | `_initialize()` 只声明 `tools` | 声明 `resources` 却不响应，客户端会卡在列表请求上 |
| **Windows 默认 GBK** | `serve()` 显式包 UTF-8 的 `TextIOWrapper` | 中文参数解码失败，表现成"协议不通" |

## 附：一句话总结每个环节

| 环节 | 一句话 |
|---|---|
| 建库 | 文档切块 → 建倒排表 + 向量表 + 权限元数据 |
| 第 0 步 | 组装 messages，历史打包成一条 user 消息 |
| ReAct 循环 | 调 LLM → 执行工具 → 结果回填 → 再来一轮 |
| 工具① 改写 | 把"那…"这类追问变成可独立检索的问题 |
| 环节 A 权限 | 先算出可访问集合，无权内容根本不参与检索 |
| 环节 B 稀疏 | BM25 看字面：词出现了吗、几次、文档多长 |
| 环节 C 稠密 | 向量看语义近似（本项目用哈希投影，非神经嵌入） |
| 环节 D 融合 | RRF 只用名次，绕开量纲问题 |
| 环节 E 重排 | 三个可解释信号精排，**并产出拒答信号** |
| 环节 F 判证据 | 覆盖率 AND 连续命中 AND 非受限 → 决定答还是拒 |
| 环节 G 打包 | 完整 payload 给框架，摘要给模型 |
| 第 5 步 降级 | 预算用尽给"部分结论"，不空手而归 |
| 第 6 步 引用 | `[n] → 文档` 由框架生成并校验范围 |
| 第 7 步 拒答 | 识别三类拒答（无依据/证据不足/权限） |
| 第 8 步 记忆 | 记入会话历史，供下一轮改写用 |
| MCP 出口 | 复用同一份注册表，role 服务端绑定，只暴露检索与列表两个只读工具 |
